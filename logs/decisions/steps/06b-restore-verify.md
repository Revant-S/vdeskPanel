# Step 6b: restore and verify

Branch `feat/06b-restore-verify`. New packages `internal/restore` (Restorer) and `internal/verify` (Verifier). Neither imports `syncer`. Join (building a fresh device's index from Drive) belongs to the incoming step, which is being built at the same time. The restore tests simulate a fresh device instead: they free every body of a synced device and set its files to CloudOnly.

## Changes to existing packages

- **cache: `Entry.EnsureCompleteParallel(ctx, parallel)`** (new file `parallel.go`). It fetches the header, lists the missing spans of every aligned run, and fetches them on an errgroup with `SetLimit(parallel)`. Each range is one run at most (8 MiB by default). After each range lands, its bitmap is stored with `context.WithoutCancel`, so a kill or pause right after a download still records it and a restart never fetches it again. The existing `EnsureComplete` is unchanged.
- **cache: `object.bitmapMu`.** Parallel fetches could otherwise store an older bitmap snapshot over a newer one. `storeBitmap` now clones and stores under this mutex. Nothing changes for sequential callers.
- **remote: bug fix in `Bodies.FetchRange`.** `drive.Client.DownloadRange` writes at absolute offsets, but the cache's `SegmentFetcher` contract says relative to the range start. Every segment after the header landed at twice its offset, so any CloudOnly read through the real client failed authentication. Nothing exercised that path until now. A small `rangeRelative` writer fixes it.
- **remote: new `Verify` adapter** (ListChildren, DownloadAll). It translates `drive.ErrNotFound` into `verify.ErrRemoteNotFound`.

## restore

- **API.** `New(ctx, Deps, Config) (*Restorer, error)`. It takes a ctx and returns an error because it loads the pause flag and wanted set from `kv`. `Run(ctx)`, `RunOnce(ctx)`, `Kick()`, `Pause(ctx) error`, `Resume(ctx) error`, `Want(ctx, ids...) error`, `RequestLocal(ctx, ids) error`, `Progress() Progress`, `Failures() []FileFailure`. Pause, Resume and Want take a ctx and return an error because they persist state.
- **`RunOnce`** downloads everything due now and returns each file's failure joined together. Tests and a future daemon "restore then verify" step use it. `Run` loops on `RunOnce` and waits for `Kick`, ctx, or `RetryFailedAfter` (default 1 min) between rounds. A pause ends a round early without an error.
- **Modes.** `RestoreEverything` (zero value, the spec default) handles every live file. `OnDemand` handles only wanted files. In both modes wanted files go first, then files in size order, smallest first. `RequestLocal` expands folders to their live files. The wanted set is persisted in `kv` (`restore.wanted`), so a `vault download` survives a restart. Entries are dropped when the file no longer needs a body.
- **Live** means `TrashID == ""`, the tombstone rule (`DeleteVer` zero or `ContentVer` after it), `KindFile`, and not `LocalOnly`. A body is needed when the state is CloudOnly or Partial and the object has a DriveID and a 16-byte BodyID.
- **Authentication after download.** Range fetches store ciphertext without checking it. The restorer reads the whole body through the entry before marking it Local. A bad segment is refetched once by the cache (R3). If it fails again, that file's failure is recorded and the file stays CloudOnly. Other files carry on.
- **Marking Local** happens in one index transaction, and only if the object is still live, still needs a body and still has the BodyID that was downloaded. A local write (Dirty) or a remote change in the meantime wins. If a download fails and the object has changed since (for example `ErrBodyMismatch` after a remote update), the failure is dropped and the next round picks up the new version.
- **D38.** `Deps.UploadsPending func() bool` is checked before each file starts. While it returns true, the restorer polls every `YieldInterval` (default 250 ms). A file already downloading finishes. The daemon should wire this to `Outgoing.Backlog` > 0 or to pending ops.
- **Pause** persists `restore.paused` and cancels the round in flight. Every range that finished is already in the bitmap.
- **Parallelism.** Up to `Files` (4) files at once, and up to `RangesPerFile` (4) range requests for each file. That gives at most 16 requests in flight. This follows the spec's two worker rows taken literally.
- **Progress** counts files and bytes per round at file granularity. A partly downloaded file counts as not done. `Complete` is set when a round ends unpaused with every counted file Local.
- **Not done here.** The tree's in-memory `State` isn't updated. `Deps.OnLocal(id)` is the hook the daemon or workspace can use for that. The spec's "restore ends with a shallow verify" belongs to whoever wires the two together (daemon).
- **Kill test.** A drivefake fault whose `Match` never matches cancels the restore ctx on the second segment request for the 20 MiB file. The device is then restarted, and a new restorer finishes the job. For every file, the byte ranges served by the fake (header included) must not overlap.

## verify

- **API.** `New(Deps, Config) *Verifier` and `Verify(ctx, deep) (Report, error)`. `Report` has counts and `Problems []Problem{ID, Path, Kind, Trashed}` sorted by path. The kinds are `missing on Drive`, `checksum mismatch`, `failed authentication` and `body identity mismatch`. The error is only for a verify that couldn't finish, such as a listing failure or a locked keyring.
- **Shallow** walks the tree level by level from `Config.TreeFolderID` and makes one `ListChildren` per folder, with up to `Listings` (8) in parallel. It matches index children by DriveID. A missing folder is reported once and its subtree is skipped. Objects with no DriveID yet (never uploaded) are skipped, since "not backed up" is the backlog's job. After the tree comes one listing of trash/: every trash record with a DriveID must be in it. A file whose object row still points at the same Drive file is checked against that row's MD5 (D32).
- **Deep** downloads every body that the shallow pass found and whose MD5 matched, both tree and trash, with up to `Downloads` (4) in parallel. Each body goes into a temp file under `Config.TempDir`. The file only ever holds ciphertext. It's checked with `vaultfile.VerifyBody`. If authentication fails, the problem is `failed authentication`. If the header BodyID differs from the index, or `ContentMAC(sha256)` differs, it's `body identity mismatch`. MD5 isn't recomputed in deep mode, because a byte flipped on Drive must show up as an authentication failure, not a checksum one.
- **Keyring lock.** `VerifyBody` runs inside `Keyring.Use`, so a lock waits until the body being checked is done. The cache's `ContentCipher` works the same way.
- **Names.** Paths are decrypted with `NameDecrypter` (`crypto.KeyringNames`) from the index snapshot, and only into the report. Logs carry oids only.

## Tests (`go test -race`)

- cache: parallel fetch overlaps requests (max in flight between 2 and 4, each range no longer than one run). A fetch cancelled mid-body and resumed in a new cache fetches no range twice.
- restore (devicetest): full restore is byte-identical, and reading back makes no downloads. Ranges for the 20 MiB file are no longer than 8 MiB and don't overlap. Kill mid-restore, restart and resume: no byte range downloaded twice. Pause persists across restart. Pending uploads stop all downloads until cleared. A corrupted remote body fails only that file. On demand with `Run` + `RequestLocal(folder, file)` makes exactly those files Local.
- verify (devicetest): a healthy vault passes shallow and deep (3 folders listed, 3 files, 1 trash item, 4 bodies). `CorruptContent` is found by deep verify only, with exactly that file. A file deleted on Drive is reported missing by both passes. A deleted folder is reported once. A deleted trash item is reported missing with `Trashed`. Index MD5 and ContentMAC tampering produce `checksum mismatch` and `body identity mismatch`.
