# Step 3b: tree and cache

Branch `feat/03b-tree-cache`. Packages `internal/tree` and `internal/cache`. Dependencies added: `golang.org/x/sync v0.24.0` (errgroup, already in the plan) and `github.com/bits-and-blooms/bitset v1.26.0` (in the plan's extra-package table).

## tree

- `Build` is a free function returning `*Tree`, as in the plan. Rows may come in any order. Names are decrypted in batches of 256 rows on an errgroup with `SetLimit(workers)`, and linking happens after decryption on one goroutine, so the result is the same whatever the worker count or row order.
- Build refuses duplicate names under one parent, unknown parents, a file as parent and cycles (any object not reachable from the root). The index is never supposed to hold these. Conflict renames (R16 row 8) must happen before rows are written. If this turns out too strict at unlock, it could log and skip instead, but failing loudly seemed safer for now.
- A row whose ID is `model.RootID` only updates the root's mtime and state. The root has no name and is never decrypted.
- `Update` changes only metadata. If parent, name or kind differ it returns `ErrPlacementChanged` (wraps `fs.ErrInvalid`), so a placement change can't slip past `Move`'s checks.
- `Move` onto the entry's own current place is a no-op. Onto any other occupied name it returns `fs.ErrExist`. A rename-over calls `Remove` on the target first.
- `Remove` returns the subtree in pre-order: the removed entry first, children in name order.
- `Aggregate` counts Local and Dirty files toward `local`. Partial files count as 0 local bytes because the tree doesn't know which segments are present. Corrupt files are also left out of `local`. If the panel needs more precision, the caller can add bitmap counts.
- Extra: `Len()`, which the tests use.

## cache

- **Signatures that changed from the brief:**
  - `New(dir, Deps, Config) (*Cache, error)`, following the plan's Deps+Config convention. `Config.RunSegments` defaults to 128.
  - `Create`, `Free`, `Replace` and `Truncate` take a `ctx`, because they write the bitmap store.
  - `Open` is read-only. `OpenWritable` has the same arguments and is counted as a writer, which is how `Free` knows to return `ErrBusy`.
  - The snapshot result type is `SnapshotFile` (it also includes `PlaintextSize`).
  - `Deps.Content` is `ContentCipher func(use func(cipher.AEAD) error) error`, so the daemon can wrap `Keyring.Use` and the keyring lock is held only while a body key is wrapped, unwrapped or resealed.
- **One shared object per oid.** Every open entry of an oid shares one `vaultfile.Body`, one size and one bitmap, with reference counts under the cache mutex. Two handles with separate Bodies would each track size on their own and overwrite each other's segments.
- **Bitmap record as completeness marker.** If an oid has no stored bitmap, its body is local-authored and complete (Create, after the first mutation, Replace, Free). If it has one, the body is a mirror of the remote body (the R2 case b invariant). `BitmapStore.PutSegmentBitmap(ctx, id, nil)` deletes the record. The index implementation has to honour this. `Snapshot` relies on it to decide whether a body that isn't open is complete, since it gets no state from the caller.
- **Opening by state.** CloudOnly and Partial open a mirror. If the file has the wrong length, a header with a different BodyID, or no bitmap record, it is stale: it's reset to an empty hole-filled file of the final ciphertext size and an empty bitmap is stored. This covers R17b: the caller updates `body_id` and reopens. Local, Dirty and Corrupt are trusted as complete, and the plaintext size comes from the file length, not from the argument, because the index size can lag a crash mid-write. `Entry.Size()` reports the real size. A wrong state from the caller (Partial for a Dirty file) would throw away local data, so the workspace must pass index state.
- **Fetching.** The header is fetched alone (`[0,128)`) into memory, its BodyID is checked against the expected one, and only then is it written. That is one extra ranged request per cloud-only open, kept for simplicity. A mismatch returns `ErrBodyMismatch`, which also matches `vaultfile.ErrTampered`, so the caller can poll and retry (A4). Segments are fetched in aligned runs of `RunSegments`. Within a run only the missing contiguous spans are requested. The fetcher writes the range's first byte at offset 0 of the given `io.WriterAt`, and the cache passes an `io.OffsetWriter` over the body file.
- **No fsync before storing the bitmap.** If the bitmap outlives its data after a power cut, the stale segment fails AEAD and a mirror refetches it (R3), so the fsync isn't needed. `Entry.Sync` fsyncs the body file for writers.
- **R3.** A present segment that fails AEAD in a mirror is cleared, stored and refetched once per segment per read. If it fails a second time the error wraps `vaultfile.ErrTampered` (the remote copy is bad). A local-authored body returns `ErrCorruptBody` wrapping the `*vaultfile.SegmentError`, and logs the oid and segment index. The caller maps this to EIO and marks the object Corrupt. A Snapshot whose Reseal hits a bad segment also returns `ErrCorruptBody`.
- **R1.** `WriteAt` and `Truncate` on an incomplete body return `ErrIncompleteBody`, except `Truncate(0)`, which starts a fresh body (new key, new BodyID) with no fetch. `EnsureComplete` fetches everything. The first mutation turns a complete mirror into a local-authored body and deletes its bitmap record, all under the object lock, so a segment dropped at the same moment can't get past the check.
- **Prefetch.** A read is sequential when it starts where the handle's previous read ended (the first read at offset 0 counts). It then starts one background fetch of the next run. There is at most one prefetch per object. It runs on the object's context, a child of the cache's root context, and is cancelled and waited for when the object closes, is detached, or the cache closes. Fetches and body replacement (`Truncate(0)`) are serialized by a per-object fetch mutex, so a prefetch can't write into a new body.
- **Replace and Free detach open entries.** The object is dropped from the cache map, and its entries keep their file descriptor (the old inode). They can still read present segments. A missing segment returns `ErrDetached`, and they never touch the bitmap store again. Writes through a detached writer reach only the old inode, which is the R9 "detached handle" behaviour. `Free` refuses with `ErrBusy` only for open writers. The Dirty and Corrupt refusals (R30) are the caller's job because the cache doesn't know index state. `Replace` doesn't refuse writers, because rename-over has to replace a target that is still open (R9).
- **Snapshot** opens the body if it isn't open (by the bitmap rule above), requires completeness, reseals into `snapshots/<batchID>/<oid>` with `O_TRUNC` (so re-snapshotting on resume overwrites), fsyncs the file, the batch dir and `snapshots/`, and removes the partial file on error. Writers wait on the Body lock while the copy runs. No FICLONE (A8). `RemoveSnapshot` also removes the batch dir once it's empty.
- Object and batch IDs are checked against `[0-9A-Za-z_-]` because they become path components.
- Not built: a cache-level `Rebind`. R10 adoption can be done with `Replace(target, BodyPath(source))`, because the adopted source is always a complete local body.
